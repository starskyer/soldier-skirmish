项目完成于 2024 年 1 月，是作者刚开始学习 C++ 时独立编写的课程大作业，当时在 Visual Studio 上可以运行；目标是完成课程功能，没有做系统的风险评估。这个历史运行情况与下面的缺陷分析可以同时成立。

本次没有执行原游戏二进制，也没有重新编译游戏。结论分为：

- **确定缺陷**：从源码即可确认存在错误的访问、未初始化读取、遗漏的释放等。触发后的表象仍可能不固定。
- **交错风险**：源码允许某种线程执行顺序，但是否在某局出现、多久出现，需要运行验证。普通共享变量的数据竞争本身可以静态确认，具体崩溃方式不能预言。
- **条件风险**：需要资源损坏、修改参数、启用未使用功能或未来改变对象销毁方式才会暴露。
- **设计取舍**：影响扩展、效率或游戏规则，但缺少课程需求依据时，不把它直接判成“做错了”。

“未定义行为”是 C++ 对这类程序不给出正常行为保证的术语，不等于每次运行都会崩溃。某台电脑、某个 Debug 构建完成过演示，能证明当次功能跑通；它不排除其他交错或构建方式下的问题。

## R01：边界判断写了，但发生在越界读取之后

原位置：`soldier_move.cpp:13` 的 `validSquare()`；`chessboard.cpp:192` 的 `getSquare()`。

```cpp
bool inbound = (0 <= pos && pos < chessboard->getSize());
bool isObstacle = (chessboard->getSquare(pos)->type != 0);
bool hasSoldier = chessboard->getSquare(pos)->hasSoldier;
bool hasBase = chessboard->getSquare(pos)->hasBase;
return inbound && !isObstacle && !hasSoldier && !hasBase;
```

最后的 `&&` 有短路规则，但前面三条读取早已执行。`getSquare()` 也只是返回 `&(chessboard[pos])`，不会检查范围。因此 `pos=-1` 或 `pos=size` 会先访问数组外的对象。

这不是仅在自定义地图上才可能出现：默认地图的出兵格 61 可以通向左边缘格 60。搜索展开格 60 时，`surroundSquare()` 会把左邻居设为 `-1`，再调用 `validSquare(-1)`。相同问题出现在上下边缘的候选格。

本次用 Python 按源码逻辑做了小型推演，确认默认地图可达格 60，候选邻居包含 `-1`；这是算法推演，不是 C++ 程序运行结果。越界访问可能碰巧读到仍映射的内存，所以它能够和当年“运行成功”共存。

修复方向：先 `if (!inbound) return false;`，再读取棋盘。上一轮整理已经这样修正；其他直接使用位置下标的接口仍需要明确约束。

## R02：互斥锁只覆盖部分写操作，没有建立完整的同步规则

原位置：`chessboard.cpp:171`、`attackBehavior.cpp:31`、`model.cpp:90`、`model.cpp:103`、`view.cpp:205`、`vision.cpp:32`。

主要共享状态及访问者：

| 状态 | 写入 | 读取 | 缺口 |
| --- | --- | --- | --- |
| `Square::hasSoldier/soldier` | 移动、出兵、击杀 | 决策、寻路、攻击、渲染 | 读取方普遍不持有同一把锁 |
| `Soldier::currentHP` | 其他士兵的攻击线程 | 自身行动线程、渲染线程 | 扣血本身也没有统一锁保护 |
| `Base::currentHP` | 兵种攻击线程 | Model 等待胜负、出兵线程、UI | 普通 int 并发读写 |
| `Chessboard::pause` | UI 线程 | 所有行动线程 | 普通 bool 不是线程同步机制 |
| `Chessboard::busy`、`View::busy` | 多个通知者与 UI | 通知者、UI、Model | 检查并设置不是原子事务 |
| `soldiers` 向量 | set/remove | 视野遍历 | 并非每次视野更新都持有棋盘锁 |
| `hasVision` 数组 | 模拟线程更新 | UI 绘制 | 数组本身也缺少同步 |

C++ 中，无适当同步的冲突访问、至少一方写入且不是原子操作，会构成数据竞争。这里不只是“可能晚读到一帧”：语言层面已经不保证程序正常行为。[C++ 工作草案：数据竞争](https://eel.is/c++draft/intro.races)。

例如两个攻击者同时执行 `currentHP -= atk`，可能丢失一次伤害；检查 `hasSoldier` 后，格子指针也可能马上被另一个线程清空。UI 的 `Square square = ...` 只是复制一次共享结构，复制动作本身没有同步，复制的指针仍指向共享士兵，不能把它当成安全快照。

把 bool 改成 `volatile` 不能解决线程同步。把所有数字单独改成 `atomic` 也不能保证“格子状态、对象指针、列表和生命值”作为整体一致。需要先定义哪些状态由谁维护，再统一保护事务或传递不可变快照。

## R03：规划、确认和落位分开，锁内仍可能写入错误状态

原位置：`soldier_move.cpp:178`、`chessboard.cpp:171`、`base.cpp:42`。

`Soldier::move()` 在取得 `move_mtx` **之前**运行 `findPath()`，锁内不重新检查 `path[0]` 是否仍为空，也不确认原位置是否仍属于自己。

一个具体执行顺序是：

| 步骤 | 士兵 A | 士兵 B |
| --- | --- | --- |
| 1 | 发现格 P 为空，路径第一步是 P | |
| 2 | | 也发现 P 为空，路径第一步是 P |
| 3 | 取得移动锁，把自己写入 P，释放锁 | |
| 4 | | 取得移动锁，直接把 P 的指针覆盖为 B |

锁确实让两次落位依次执行，但没有让第二次落位继续合法。`setSoldier()` 直接设置指针并把对象追加到 `soldiers`；它不拒绝占用格、不去重，也不验证归属。结果可能是列表里有 A 和 B，棋盘 P 却只有 B。A 下次按自己的 `pos` 清理 P 时，又可能移除 B。

出兵只在锁外检查出生点，而出兵不遵守 `move_mtx`，所以“出兵”和“移动进入出生点”也可能互相覆盖。

另一个交错是：A 判断自己还活着后开始寻路；期间被其他线程击杀并从棋盘移除；A 随后取得移动锁，却不再检查生命值，仍把自己插回棋盘。它下一次行动循环可能因 HP 为 0 退出，但棋盘可能留下死亡士兵占格。

修复方向：提供一个完整的 `tryMove(id, from, to)` 事务，锁内重新验证对象存活、起点归属、终点空闲，然后一次性更新位置。失败则放弃或重新规划。出生、死亡也应遵守同一套状态规则。

## R04：攻击的是“之前看见敌人的格子”，未必还是那个敌人

原位置：`soldier.cpp:20`、`soldier.cpp:68`、`attackBehavior.cpp:31`。

`decide()` 返回的是格子下标。随后调用攻击策略时，`SoldierNormalAttack::attack()` 只检查那里是否还有士兵，不核实队伍、身份、距离或攻击者是否仍存活。

可能出现：

1. A 决策时看见格 P 有敌兵 E。
2. E 移走，同队士兵 F 进入 P。
3. A 开始攻击，直接扣除 P 当前士兵 F 的 HP，造成友伤。

也可能在 `hasSoldier` 检查后，其他线程刚好清空该格，下一条 `soldier->currentHP` 便解引用空指针。反复通过 `getSquare(pos)` 获取指针扩大了这种检查与使用分离的问题。

这里应准确区分：原实现几乎不删除死亡士兵对象，所以不能把所有此类问题直接叫作“释放后使用”；当前更直接的风险是空指针、对象认错和状态失配。若以后开始回收士兵，才会额外引入生命周期风险。

修复方向：用稳定的对象 ID 表达目标，执行攻击时在一次受保护的操作内复核存活、敌我关系、射程与目标位置。单纯给扣血那一行加锁不够。

## R05：观察者通知变成了“持锁等待窗口确认”

原位置：`chessboard.cpp:171`、`model.cpp:90`、`view.cpp:318`。

当前调用链是：

```text
setSoldier/removeSoldier 取得 mtx
  → 更新棋盘/士兵列表
  → Chessboard::notifyObservers 更新视野
  → Model::notifyObservers 设置 View::busy=true
  → 原地等待 UI 把 busy 改回 false
  → mtx.unlock()
```

这会把模拟更新速度与 UI 绘制速度绑定。移动时外面还可能持有 `move_mtx`，击杀时可能持有 `atk_mtx`，一次慢绘制会阻塞一批模拟工作。

一个可说明永久等待的交错：UI 处理了关闭事件，并完成最后一次 `busy` 检查；工作线程此时才设置 `busy=true` 并等待；UI 随后退出循环，再也没有人把它清零。进程很快结束可能掩盖这个问题，但若以后增加重开、等待线程退出或完整析构，就容易出现关不干净、join 等不到等现象。

刷新也可能丢失：`Model::notifyObservers()` 在 `busy` 已为 true 时直接跳过，新修改发生于一帧绘制过程中，UI 最后把标志清为 false，却没有保留“期间又发生了变化”的状态。棋盘的 `busy` 也有相似问题。

这不是已经证明存在某个固定的“双互斥锁反向获取”死锁；源码能直接支持的是持锁等待 UI、退出路径失去应答和通知丢失的风险。

修复方向：模型完成一次更新后发布快照或通知消息，不在持锁区等待 UI。UI 取最新状态绘制；停止流程能唤醒所有等待者。

## R06：detach 释放了线程句柄的管理责任，没有替程序管理结束

原位置：`controller.cpp:15`、`model.cpp:54`、`base.cpp:50`、`soldier.cpp:97`。

控制线程、出兵线程、士兵线程都被 detach。没有统一的“对局结束/应用关闭”信号，也没有停止后等待所有工作线程的过程。

- UI 关闭只是 `View::SDLWork()` 的局部 `quit=true`，模拟线程不知道它。
- 士兵循环只看自身 HP，胜负确定并不会统一停止存活士兵。
- 存活基地的出兵循环也不会仅因敌方基地死亡而自动结束。
- `removeSoldier()` 只是从格子和列表移除对象，不能直接停止对应线程；代码中的停止意图依赖它之后重新检查 HP。
- 若死亡时线程正在 `while(pause);` 等待，它也不会立刻因死亡退出。

`detach()` 后线程在真正结束时可以释放它自己的线程资源，因此不能笼统说“detach 必定泄漏线程资源”。缺失的是应用层的取消、等待和对象生命周期管理。[C++ 工作草案：join 与 detach](https://eel.is/c++draft/thread.thread.member)。

原入口把 Model、Controller 分配在堆上且不删除，暂时减少了“工作线程访问已析构模型”的机会，但这是以泄漏回避生命周期问题。以后不能只加几条 `delete` 就认定修好。

改成 `shared_ptr` 只改善所有权，不能修复数据竞争；改成 `jthread` 也要真正接入停止条件，并处理工作线程等待 UI 的情况，否则自动 join 仍可能卡住。

## R07：两个只在注释中创建的资源，退出时却真的销毁

原位置：`view.h:12`、`view.cpp:342`、`view.cpp:398`。

`resultRenderer`、`resultWindow` 没有初始化，对应创建代码已经注释掉，但清理仍执行：

```cpp
SDL_DestroyRenderer(resultRenderer);
SDL_DestroyWindow(resultWindow);
```

未初始化指针不等于空指针，SDL 不能替调用方把垃圾指针识别成“未创建资源”。它可能使游戏正常结束后，反而在清理阶段崩溃。

整理版已把资源指针初始化为 `nullptr` 并补充关闭入口。后续仍建议用 RAII 封装资源，覆盖初始化到一半失败的清理路径。

## R08：启动时视野数组存在，但内容尚未建立

原位置：`vision.cpp:13`、`vision.cpp:43`、`controller.cpp:10`、`view.cpp:207`。

`new bool[size]` 没有初始化每个 bool。构造棋盘时创建三种 Vision，但没有立即计算视野；Controller 随后先调用 `printBoardSDL()`，再进入事件循环。首帧读取的就是这些未初始化内容。

这说明首帧显示问题不一定是图片丢失。需要先建立一份确定的初始视野，再读取。

上一轮整理将数组改成零初始化，消除了未初始化读取，但**零初始化并不等于算好了基地视野**：开始前仍可能全是迷雾，直到第一次状态通知刷新。这个视觉行为尚待补齐；不能把局部修复写成整个初始视野逻辑已经正确。

## R09：固定演示资源可用时，许多输入和初始化失败分支没有被走到

原位置：`chessboard.cpp:36`、`controller.cpp:10`、`view.cpp:24`、`view.cpp:43`、`view.cpp:64`。

地图/基地读取存在这些条件风险：

- 文件打不开仍继续 `getline` 和 `stoi`，可能抛异常退出。
- 声明总格数小于真实地图字符数，会把类型写到已分配数组外。
- 地图没有有效行时，`length` 没有可靠初值；空末行可能把长度变成 0，之后 `size / length` 出问题。
- 各行宽度不一致时，总格数与坐标换算失配。
- 不核实队伍是否为 1/2、位置是否在范围内、出生点是否可通行；例如不合法队伍会影响 `bases[team-1]`。
- Windows 下原工作目录能正确找到资源，但从 exe 所在目录、另一终端或另一平台启动未必能找到同样的相对路径。

SDL 部分也有失败传播问题：

- `SDLinitialize()` 返回 false，Controller 仍继续打印棋盘。
- 七个纹理及字体打开后未检查整体结果，最后依然输出初始化成功。
- `CreateFontTexture()` 失败时不保证写入宽高，而调用者继续用这些变量构造矩形；第一次文字渲染就失败时，可能读到未初始化尺寸。
- 只请求硬件加速渲染器，没有软件回退，因此某些图形环境初始化失败后仍走到上述路径。

这些是“换电脑/改资源时缺少保护”的问题，不是对原来资源一定有损坏的判断。整理版增加了入口资源校验、初始化失败退出、纹理/字体检查及软件渲染回退；它们尚未做真实 SDL 运行回归。

## R10：短演示不显著，长对局会积累的泄漏

原位置：`soldier_move.cpp:109`、`view.cpp:143`、`base.cpp:15`、`soldier.cpp:132`、`main.cpp:11`。

1. `findPath()` 每次 `new int[size]`，返回时没有 `delete[]`。默认 400 格、常见 4 字节 int 下，每次约 1600 字节；一万次搜索约泄漏 15.3 MiB，不计分配器开销。这是静态算例，不是实测泄漏速率。
2. 每次绘制创建 Start、Pause、Change Vision 的文字纹理，用完没有销毁；胜负文本也有相同遗漏。帧数越多，渲染资源积累越多。
3. 死亡士兵从列表移除，但对象和它的攻击策略没有被释放。删除容器中的一个裸指针，不会自动删除它指向的对象。
4. Model、Chessboard、Controller、View、基地、Vision 及相关数组没有形成完整的释放链。

进程退出时操作系统会回收地址空间，但这不能避免运行期间增长；如果以后在同一进程连续开多局，问题会更加明显。整理版已修复前两类，其他对象需要和线程结束策略一起设计。

## R11：补内存释放时，基类接口还有一个后续陷阱

原位置：`soldier.h:7`、`attackBehavior.h:5`、`vision.h:5`。

这些类有虚函数，却没有虚析构函数。当前没有通过这些基类指针删除派生对象的执行路径，因此不把它记成“现在已经发生的错误删除”。

但未来如果用 `Soldier*`、`AttackBehavior*`、`Vision*` 或默认 deleter 的相应 `unique_ptr` 销毁派生对象，就需要先补齐正确的多态析构约定与资源所有权。[C++ 工作草案：delete 表达式](https://eel.is/c++draft/expr.delete)。

## R12：空闲、暂停和等待胜负时，线程仍在高速循环

原位置：`model.cpp:76`、`model.cpp:98`、`base.cpp:41`、`soldier.cpp:70`、`soldier_move.cpp:181`、`view.cpp:320`。

`while (pause);`、`while (busy);`、等待基地死亡的空循环和 UI 无事件循环都没有阻塞或限速。它们不断读取状态，即使没有有意义的工作也消耗 CPU。

这里有两层问题：普通 bool/int 的跨线程轮询先有 R02 的正确性问题；即使加上原子同步，忙等待仍然浪费执行时间。`sleep_for()` 也不是线程同步操作，不能靠在循环中随便睡一下来证明安全。

每个士兵又独占一个系统线程，线程数量随存活士兵增加，带来调度和栈资源成本。没有负载测试，不能给出“到多少士兵一定崩”的阈值。

游戏节奏也不是严格的模拟时间：一次动作耗时包括锁等待、通知 UI、计算与 sleep，暂停只阻挡部分执行点，已经睡下的线程并未冻结自己的计时。于是实际速度受到帧率、调度和暂停时机影响。

## R13：寻路基本思路可行，但与动态棋盘的衔接不完整

原位置：`soldier_move.cpp:39`、`soldier_move.cpp:104`、`soldier_move.cpp:146`。

主路径采用 BFS 标记层数后沿层数回溯，在固定、合法的棋盘上是成立的思路。主要问题发生在外围条件：

- 搜索读取的是会同时变化的棋盘，结果生成后也没有在落位前复核，见 R03。
- 把其他士兵作为完全不可通过的障碍，拥堵时可能暂时无路；没有预订、排队或统一冲突裁决。
- 无路时通过 `marks+1` 选择后继，实际上是在远离本次起点的 BFS 层次上继续走，并不是任意随机漫步。走到没有更大层号的格子会返回原位置，后面可能重复原地等待。这可以是简化策略，但不保证趋近敌方基地。
- 目标被占用时，`while(targets.empty())` 随机重选目标，没有次数上限或“本轮先等待”的出口；其中也不检查暂停、生命值、对局停止。没有可用空格或高拥堵时可能长时间占用 CPU。
- 每走一小步重新搜索；在网格规模 V、移动步数 S 下，一轮移动可能执行约 S 次 O(V) 的搜索。原地图只有 400 格，成本未必严重，扩大地图才更值得优化。

有两个容易误报的点需要说明：BFS 内部每次 pop 后已经检查队列是否为空，不能只因为看见 `front()` 就认定一定空队列访问；正常内部调用在目标不等于自身、剩余步数为正时也有生成路径的逻辑，不能只凭 `path[0]` 没有显式检查就断言默认场景必然访问空 vector。需要证明对应前提被破坏。

## R14：反复 srand 使随机行为相关，也不利于复现

原位置：`base.cpp:39`、`soldier_move.cpp:97`、`soldier_move.cpp:158`。

出兵以秒级时间播种，寻路分支按时间重新播种，目标重选又按秒播种。两次初始化拿到相同种子，就可能重复同一段序列；两个基地接近同时启动，也可能出现相关的出兵模式。

各平台运行库对随机状态的组织不宜一概而论，所以本报告不把每次 `rand()` 都直接判为某个具体平台的数据竞争。可以确定的是程序没有自己管理随机引擎、种子和可复现实验条件。

建议在对局开始时创建引擎并保存种子，后续复用。整理版只替换了 `randomNext()` 的一支；出兵和目标重选仍需统一。如果未来改成单线程更新，使用一个由对局对象持有的引擎通常更容易复现。

## R15：基地攻击代码存在，当前没启用，直接启用又会暴露另一问题

原位置：`model.cpp:64`、`base.cpp:59`、`attackBehavior.cpp:12`。

实际入口从 Controller 调用的是 `Model::start_test()`；里面基地攻击线程的启动代码是注释。`Model::start()` 的当前实现也只启动出兵，所以不能因为有 `Base::attack()` 就认为实际对局包含基地反击。

如果当时作业不要求基地反击，这可以是未用功能，而非验收失败。但未来启用时要注意：

```cpp
if (target >= 0)
    attackBehavior->attack(target);
else
    sleep_for(...);
```

`BaseAttack::attack()` 本身也没有等待。因此有目标时会连续攻击，伤害速度由 CPU 和锁等待决定，而不是清晰的攻击周期。攻击策略注释中“会花一个周期”的约定没有在这个分支兑现。当前未启动该功能，所以这不是原有对局必然存在的高速攻击现象。

## R16：异常和对象构造方式使恢复、测试、重开变得困难

原位置：`chessboard.cpp:171`、`controller.cpp:7`、`base.cpp:50`。

手动 `lock()/unlock()` 之间可能执行 vector 分配、视野计算、通知等会抛异常的操作。若异常离开这段代码，锁不会自动释放；后台线程又没有捕获异常的边界，未处理的异常可能直接结束整个进程。

创建士兵后还要创建线程，如果线程创建失败，没有一个完整的回滚流程来撤销已放到棋盘的士兵。资源紧张时这类路径才容易暴露，不能凭静态审查给出出现频率。

Controller 的构造函数直接初始化窗口、绘制并进入整个事件循环，所以 `new Controller(...)` 要等游戏结束才返回。这个过程中 `this` 还被交给 View 使用。当前顺序不等于必然非法，但它混合了“建立对象”和“运行应用”，很难分别做初始化失败检查、单元测试或多局重开。

工程层面还包括：大量可直接改写的 public 成员和 friend；用整数区分兵种、动作和视野；`Model::start()` 与 `start_test()` 重复；未使用的变量和大段注释分支。它们主要增加维护与理解成本，不应和越界、数据竞争放在同一严重等级。

## 其他细节与不应过度判断的部分

- `posAround(center, 0, 0)` 会返回两次中心格。按源码推演，`posAround(21, 0, 1)` 得到 10 个条目、9 个不同格子：d=0 时顶部和底部循环都插入中心。目前设基地和视野只是重复赋值，影响较小；以后按条目累加伤害或数量时才可能产生实质重复计算。
- 攻击/视野范围按方形环枚举，近似切比雪夫距离；移动用四邻接 BFS。对角能攻击但不能对角移动可以是一种规则，不能仅因两者不一致就判错。
- 视野和攻击没有按障碍物做射线遮挡；`VisionAll` 是两队当前视野的合并，不是全图全知。是否符合课程要求需要看原规则。
- 鼠标处理使用当前鼠标状态而不是事件携带的位置，且没有筛选左右键；在排队事件、快速移动或不同按键下可能出现意外触发。这属于交互细节，优先级低于状态一致性。
- 原窗口固定 1080×1230，可能超出其他显示器可用高度。这是显示适配问题，不是文件缺失。
- 原 VS 配置写死 E 盘 SDK 路径，Win32 配置也未获得与 x64 同样的依赖设置。它解释了环境迁移困难，不推翻当年指定 x64 环境下能够运行的事实。
- 当前实际 SDL 绘制发生在主线程。Model 中直接调用绘制的语句是注释，因此没有据此报告“现版本在工作线程调用 SDL_RenderPresent”。保留主线程渲染方向是合适的。[SDL2 官方线程要求](https://wiki.libsdl.org/SDL2/SDL_RenderPresent)。

## 如果以后继续维护，建议的顺序

1. **先统一模拟状态的修改线程。** 对这个体量的课程游戏，主循环按固定时间步更新出兵、移动、攻击，通常比维护每兵一个线程更简单；保留 Soldier、Factory、Strategy、Vision 等教学结构即可。
2. **再明确状态不变量。** 每个活士兵只有一个位置；每格最多一个士兵；棋盘与士兵表一致；死亡对象不能继续移动；攻击前目标仍合法。移动、出兵、死亡和扣血按完整事务执行。
3. **统一结束与资源所有权。** 定义关闭、胜负与暂停语义；先停止工作，再清理对象。用值对象、vector 和 unique_ptr 表达实际所有权，补齐多态析构；不要一律换 shared_ptr。
4. **最后做性能与展示改进。** 在正确性可控后再考虑缓存路径、减少刷新次数、自适应窗口、重新开始与可复现随机种子。

后续有可运行环境时，最有价值的回归场景是：边缘寻路；两个单位竞争同格；目标离开后友军进入；寻路过程中单位死亡；暂停期间死亡；关闭窗口时仍有通知等待；满格拥堵；缺图缺字体；损坏地图；重复开局及长时间运行。应分别用适用工具检查越界/泄漏与线程竞争，不能把一次正常对局或无窗口启动检查当作全部覆盖。

对这份历史作品更准确的评价是：当时已经把数据结构、对象协作、寻路与图形显示组合成了能够演示的作业；继续作为可维护游戏开发时，需要补上状态一致性、线程生命周期和错误处理。可以在 GitHub 同时保留这个学习阶段的事实和本次审查结果。
